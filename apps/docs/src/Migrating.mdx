# Migrating from @pitchfork-ui/react

`@pitchfork-ui/react` is being retired. The elements are the library now, and
every one of its 91 components has an element answer.

**A React application does not leave React.** `@pitchfork-ui/elements-react` is
generated from the same build by Stencil's output target and gives every element
a typed component with real event props. For 37 of the
91 components the whole move is three mechanical renames:

```tsx
import { Button } from '@pitchfork-ui/react';
<Button variant="primary" onClick={save}>Save</Button>;

// becomes
import { PfButton } from '@pitchfork-ui/elements-react';
<PfButton variant="primary" onPfClick={save}>Save</PfButton>;
```

`npm run codemod:elements -- <paths>` does exactly those three and refuses
everything else. It is deliberately narrow: a wrong automatic rewrite of a
content prop is worse than a `// TODO` pointing at the right page.

## The three things that change shape

### A content prop cannot stay a prop

A prop typed `ReactNode` has no element equivalent, because a slot takes
markup and cannot take a React tree. Where the element declares a slot of the
same name, the value becomes a slotted child:

```tsx
<MetricCard heading="Revenue" icon={<Icon name="chart-bar" />} />
// becomes
<PfMetricCard>
  <span slot="heading">Revenue</span>
  <PfIcon slot="icon" name="chart-bar" />
</PfMetricCard>
```

**But some content props are answered by a plain string prop instead**, and
those need nothing at all as long as the value is text. `pf-alert` takes
`heading` as `string`, so `<Alert heading="Saved" />` moves across
untouched — and `<Alert heading={<b>Saved</b>} />` does not, because an
attribute cannot carry markup. The codemod warns at any such call site that
passes an expression rather than a string. 4 components have props in this group, and it is the distinction a hand-written table cannot
express.

### A data prop becomes child elements

`WEB-COMPONENTS-PLAN.md` §2.1: data-driven elements take child elements, not
arrays, because a slotted child is something a framework can key, reorder and
bind to. Every consumer loop inverts:

```tsx
<Select options={fruits} />
// becomes
<PfSelect>
  {fruits.map((f) => (
    <PfOption key={f.value} value={f.value}>{f.label}</PfOption>
  ))}
</PfSelect>
```

**Not every array does this.** A chart's `data` stays a property — the rows are
bulk numbers with no identity — while its `series` become children, because
those have names and colours and a legend built inside a shadow root could never
reach a label in the light DOM. The table below says which is which per
component, derived from the element's own recorded props rather than assumed.

### An event prop gains a `Pf`

`onChange` is `onPfChange`, `onDismiss` is `onPfDismiss`. The generated
bindings expose the element's own events, which are all `pf`-prefixed so they
cannot collide with a native one. This rename is mechanical and the codemod does
it.

## Only an event prop to choose (6)

Every other prop maps one to one. The element emits a different event name than
the React prop implies, so the handler needs pointing at the right one — and
this is the quietest thing to get wrong in the whole migration, because
renaming the component and keeping the old prop **compiles, renders, and never
fires**. `<Slider onValueChange={set} />` becomes
`<PfSlider onPfChange={set} />`: `pf-slider` emits `pfChange`, not
`pfValueChange`. The codemod refuses these rather than renaming the
component and leaving a dead handler behind.

| Component | Element | How |
| --- | --- | --- |

## What is not changing

The tokens and the theming contract. `@pitchfork-ui/tokens` ships the same
`theme.css`, every `--pf-*` alias the React components read is read by the
elements too, and custom properties cross a shadow boundary — so a theme set on
`:root` reaches inside an element without any change. Dark mode is still
`[data-theme='dark']` on an ancestor.

What a consumer's stylesheet **cannot** do any more is reach inside a component
with a selector. `.pf-button` is not in the document once the element renders
its button into a shadow root. Every element exposes the boxes worth styling as
`::part()`, listed on its own reference page.

## Timeline

`@pitchfork-ui/react` is still published and still gets fixes. It is
deprecated on npm with a pointer to this page, kept publishable for a stated
window so a security patch stays possible, and removed from the repository only
after that window. Deprecation is a notice, not a removal — nothing breaks on
the day it lands.

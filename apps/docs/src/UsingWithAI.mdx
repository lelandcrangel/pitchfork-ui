# Using Pitchfork UI with AI

Coding agents know a great deal about component libraries in general and
nothing about _this_ one. Ask for a settings page and you get `severity` on an
alert, a button size of `"medium"`, and a hex colour in a `style` attribute —
because those are the odds-on answers across every library it has ever seen.

Pitchfork UI publishes its real API in three machine-readable forms so an agent
does not have to guess. All three are generated from source on every build, so
none of them can drift from the library.

They describe **the 108 custom elements**, which are the library. The
deprecated `@pitchfork-ui/react` is still covered, because it is still
published — but an agent writing new code should be writing elements, and the
preamble of each artifact says so.

---

## The difference it makes

Here is what an agent typically writes without the API:

```html
<pf-card padding="large">
  <pf-badge type="success">Active</pf-badge>
  <pf-alert severity="error" title="Payment failed"></pf-alert>
  <pf-button variant="default" size="medium">Retry</pf-button>
  <div role="button" onclick="dismiss()" style="color: #4f46e5">Dismiss</div>
</pf-card>
```

Every line of that parses, renders, and is wrong. An unknown attribute on a
custom element is not an error in HTML — it is simply ignored — so there is no
console warning and nothing fails to build. Running it through the
`validate_usage` tool gives:

```
5 error(s), 1 warning(s).

- error (line 1): `<pf-card>` has no attribute `padding`. It takes no attributes of its own.
- error (line 2): `<pf-badge>` has no attribute `type`. Its attributes are: `variant`.
- error (line 3): `<pf-alert>` has no attribute `severity`. Its attributes are: `description`, `dismiss-label`, `dismissible`, `heading`, `variant`.
- error (line 4): `variant="default"` is not valid on `<pf-button>`. Expected one of: "destructive", "ghost", "primary", "secondary".
- error (line 4): `size="medium"` is not valid on `<pf-button>`. Expected one of: "lg", "md", "sm".
- warning (line 5): Hardcoded colour `#4f46e5`. Use a CSS variable instead — component styles go through a `--pf-*` alias, never a raw value.
```

The same request, with the agent grounded in the library's API:

```html
<pf-card>
  <pf-badge variant="success">Active</pf-badge>
  <pf-alert variant="danger" heading="Payment failed"></pf-alert>
  <pf-button variant="primary" size="md">Retry</pf-button>
  <pf-button variant="ghost">Dismiss</pf-button>
</pf-card>
```

```
0 error(s), 0 warning(s).

No problems found.
```

**The element side catches one the React side could not.**
`<pf-badge type="success">` is reported, where `<Badge type="success">` was
not: a React component extends `HTMLAttributes`, so `type` is a legitimate
passthrough prop and the validator could not call it wrong without crying wolf
on every other component. A custom element's attribute set is closed, so the
same mistake becomes provable. That is five errors here against four for the
equivalent React snippet.

What it still cannot tell you is whether `title` on `<pf-alert>` was meant to
be `heading` — `title` is a global HTML attribute and valid on anything, so it
passes. The validator stays quiet wherever it cannot be sure, because a tool
that cries wolf gets switched off.

## 1. MCP server — the richest option

The [Model Context Protocol](https://modelcontextprotocol.io) server answers
questions about the library on demand, so the agent looks things up while it
works instead of being handed a wall of documentation up front.

### Install it

**Claude Code**

```bash
claude mcp add pitchfork-ui -- npx -y @pitchfork-ui/mcp
```

**Cursor, VS Code, Zed, or any other MCP client** — add it to the client's MCP
config file:

```json
{
  "mcpServers": {
    "pitchfork-ui": {
      "command": "npx",
      "args": ["-y", "@pitchfork-ui/mcp"]
    }
  }
}
```

Restart the client. The server is stdio-based and needs no API key. Everything
it answers from ships inside the package, so once running it makes no network
requests of its own — `npx` fetches the package itself on first run, and again
whenever the npm cache is cold.

### Check it is working

Ask the agent for something only the server can answer:

> Using the pitchfork-ui MCP server, what variants does `Button` take?

A grounded answer names `primary`, `secondary`, `ghost` and `destructive`. A
guess says `default` and `outline`. If you get the guess, the client has not
picked the server up — check its MCP panel or logs.

### The tools

The first four are where an agent should live. The next three cover the
deprecated React package, for maintaining code that already uses it.

| Tool                | What it answers                                                           |
| ------------------- | ------------------------------------------------------------------------- |
| `list_elements`     | Every custom element, by category — **start here**                        |
| `get_element`       | An element's props, attributes, events, methods, slots, parts and example |
| `get_examples`      | Copy-ready markup for an element, by tag, element name or React name      |
| `validate_usage`    | Check a snippet against the real API — `<pf-*>` markup or JSX             |
| `get_tokens`        | Colours, spacing, radii, typography, shadows, motion                      |
| `get_conventions`   | The house rules — naming, the variable chain, breakpoints, a11y           |
| `list_components`   | The deprecated React components, by category                              |
| `search_components` | “I need something for uploading a file” — searches the React components   |
| `get_component`     | A React component's props, defaults, a11y contract, theme variables       |

`get_examples` is the bridge off the deprecated package: handed a React name
like `Table` it answers with the element that replaces it and that element's
markup, because the React examples were removed along with their docs pages.

### Getting the most out of it

Agents reach for a tool when they know it exists and when the task obviously
calls for it. Two things make that reliable:

- **Say so once, at the start of the session.** "Use the pitchfork-ui MCP server
  for component APIs — don't guess prop names." That one line is usually enough
  for the rest of the conversation.
- **Ask for validation as part of the work,** not as a review afterwards: "write
  the settings panel, then run `validate_usage` on it and fix anything it
  reports." The agent then catches its own mistakes before you read the diff.

If your project has `@pitchfork-ui/react` or `@pitchfork-ui/elements`
installed, the server answers from _that_ copy, so it describes the version you
are actually building against rather than the newest one.

To point it somewhere else, set `PITCHFORK_UI_METADATA` in the client's `env`
block. The client is what launches the server, so exporting the variable in your
own shell has no effect on an already-configured client:

```json
{
  "mcpServers": {
    "pitchfork-ui": {
      "command": "npx",
      "args": ["-y", "@pitchfork-ui/mcp"],
      "env": {
        "PITCHFORK_UI_METADATA": "/absolute/path/to/metadata.json"
      }
    }
  }
}
```

Use an absolute path there. A relative one resolves against the client's working
directory, which is rarely your project, and a path that does not exist is not
an error — the server quietly falls back to its bundled copy and answers as if
nothing were wrong. The startup line on stderr names the file it actually
loaded, so check that if an override seems to have no effect.

To check a metadata file by hand, where the working directory _is_ yours, pass
it on the command line:

```bash
PITCHFORK_UI_METADATA=./node_modules/@pitchfork-ui/react/dist/metadata.json \
  npx -y @pitchfork-ui/mcp
```

## 2. `llms.txt` — nothing to install

- [`llms.txt`](https://lelandrangel.com/pitchfork-ui/llms.txt) — an index of every element, one line each
- [`llms-full.txt`](https://lelandrangel.com/pitchfork-ui/llms-full.txt) — the whole library in one fetch: props,
  attributes, events, slots, parts, theme variables and a worked example each

Paste either URL into any assistant that can read a link.

## 3. `elements.json` — for your own tooling

```ts
import elements from '@pitchfork-ui/elements/metadata' with { type: 'json' };
```

Every element with its props, attributes, events, methods, slots, parts and a
worked example, plus the category each belongs to and its React counterpart.
This is one of the two artifacts the files above are generated from — use it if
you are building codegen, a linter, or a docs site of your own.

The other is `@pitchfork-ui/react/metadata`, which carries the **deprecated**
React API: props, types, defaults and resolved CSS variable chains. It is still
generated because the package is still published, so an agent maintaining
existing React code can still be grounded in the real props — but it carries no
examples or descriptions any more, since those were read from docs pages that
no longer exist, and it is not what new code should be written against.

For moving that code across, the server's `get_examples` answers for a React
component name as well as an element tag or element name, so asking it about
`Alert` shows you the `pf-alert` markup. `get_element` itself takes the tag
(`pf-alert`) or the element name (`PfAlert`), not the React name.
**Foundations → Migrating** has the component-by-component mapping.

## Why it stays correct

Nothing above is hand-maintained. A build step reads the TypeScript source, the
component stylesheets, the Storybook examples and the contributor guide, and
emits the metadata; everything else is a projection of it. Add a prop and it
appears in all three surfaces on the next build.

CI fails if a component is missing from the category list, if a CSS variable
resolves to nothing, if a documentation link points at a page that does not
exist, or if any of the library's own documented examples fail `validate_usage`
— which is the strongest check available, since those examples are real working
code.

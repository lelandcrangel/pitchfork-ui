# Web components

**The 112 custom elements in `@pitchfork-ui/elements` are the library.** They
are standard custom elements, so they work in any framework and in a plain HTML
file, and the `Components` section of this site documents them and nothing
else.

`@pitchfork-ui/react` — the hand-written React component library this started
as — is **deprecated**. The notice is on npm against every published version,
and every one of its exports carries a `@deprecated` tag, so an editor strikes
the import through as you type it. It is still published and still gets fixes,
and nothing you have built on it stops working. But it takes no new components,
its documentation pages are gone, and it is removed from the repository after
**30 April 2027**.
A React application does not have to leave React to move off it: the generated
`@pitchfork-ui/elements-react` bindings give every element a typed component.
**Foundations → Migrating** has the component-by-component mapping.

Behaviour that is not about a template lives in `@pitchfork-ui/core`, which
imports nothing: anchored positioning, focus trapping, list-navigation index
maths, date stepping, chart geometry, the icon registry. The elements own their
templates and their reactivity and nothing else, which is why a fix usually
lands in core and why the three binding packages are **generated** from the
same build rather than written by hand.

## Installing

```bash
npm install @pitchfork-ui/elements
```

`@pitchfork-ui/tokens` is one of its dependencies, so the token stylesheet
arrives with it and there is nothing else to install. Load it once, by the name
the package exports — the file inside `dist/` is not an exported subpath and a
deep import of it fails to resolve:

```ts
import '@pitchfork-ui/elements/styles.css';
```

### Plain HTML

```html
<script type="module">
  import { defineCustomElements } from '@pitchfork-ui/elements/loader';
  defineCustomElements();
</script>

<pf-button variant="primary">Save</pf-button>
```

The loader registers every tag and fetches each element's code the first time
the tag appears on the page. To bundle only the elements you use instead,
import each one and register it yourself; importing the module alone
registers nothing, which is what lets a bundler leave the others out:

```ts
import { defineCustomElement as defineButton } from '@pitchfork-ui/elements/components/pf-button.js';

defineButton(); // pf-button, and any element it renders inside itself
```

With a binding package (`@pitchfork-ui/elements-react`, `-angular` or `-vue`),
do neither: each binding component registers its own tag the first time it
renders, so an app ships the elements it uses and no others. Calling
`defineCustomElements()` from the loader as well would register the same tags
again from a second build.

### React

The React bindings are **generated** from the elements by Stencil's output
target — never hand-edited — and give every element a typed component with
real event props rather than `addEventListener`.

```tsx
import { PfButton, PfTabs } from '@pitchfork-ui/elements-react';

<PfButton variant="primary" onClick={save}>
  Save
</PfButton>;

<PfTabs value={tab} onPfTabChange={(event) => setTab(event.detail.value)}>
  …
</PfTabs>;
```

A native event keeps its React name (`onClick`, `onKeyDown`); an element's own
`pf*` event becomes `onPf*`.

These bindings are what a React application uses now, and they are generated
from the elements by Stencil's output target rather than hand-written — so they
cannot drift from the element they wrap.

### Angular

Also generated, as standalone components — plus the
`ControlValueAccessor` directives that let a form control bind with
`formControlName` or `ngModel`. That capability is why the elements are
Stencil-authored rather than Lit: with Lit each accessor would be
hand-written, once per control.

```ts
import { FormControl, ReactiveFormsModule } from '@angular/forms';
import { PfInput, TextValueAccessor } from '@pitchfork-ui/elements-angular';

@Component({
  imports: [PfInput, TextValueAccessor, ReactiveFormsModule],
  template: `<pf-input [formControl]="email" label="Email" />`,
})
export class SignUpForm {
  email = new FormControl('');
}
```

The accessors are standalone directives, so import the one a control needs
beside it: `TextValueAccessor` for the text controls, `BooleanValueAccessor`
for `pf-checkbox` and `pf-switch`, `NumericValueAccessor` for `pf-slider`.
Without it Angular reports "No value accessor" for the control.

### Vue

Generated as well. Vue renders a custom element directly without any wrapper,
so these are a convenience rather than a necessity — what they add is typed
props, `@pf-*` listeners instead of `addEventListener`, and `v-model` on the
six form controls.

```vue
<script setup lang="ts">
import { PfInput, PfSwitch } from '@pitchfork-ui/elements-vue';
import { ref } from 'vue';

const email = ref('');
const dark = ref(false);
</script>

<template>
  <PfInput v-model="email" label="Email" />
  <PfSwitch v-model="dark" label="Dark mode" />
</template>
```

`v-model` binds `value` on `pf-input`, `pf-textarea`, `pf-radio-group` and
`pf-slider`, and `checked` on `pf-checkbox` and `pf-switch` — the same six
controls the Angular `ControlValueAccessor`s cover. Everything else takes
plain props and emits `pf-*` events.

## Events

Every event is a `CustomEvent` with its payload in `detail`, and the
elements follow the platform about which ones bubble.

**A form control's `pfChange` and `pfInput` bubble**, the way `change` and
`input` do, so one listener on a form hears every control in it. Only form
controls emit those two names.

**Everything else fires on the element it is about and stops there**, the
way `toggle` and `close` do: `pfOpenChange`, `pfSelect`, `pfDismiss`,
`pfSortChange`, `pfPageChange` and every container's own change event. Listen
on the element itself. Each framework binding already does, so `onPfOpenChange`,
`(pfOpenChange)` and `@pf-open-change` need nothing extra.

The reason is that containers nest. When these events bubbled, a `pf-select`
closing inside a `pf-modal` reached the modal's own `pfOpenChange` handler as
`{ open: false }`, and a `pf-switch` in a tab panel reached `pf-tabs`' change
handler as `{ value: "on" }`. So the containers' change events also have
names of their own:

| Element           | Event               | `detail`            |
| ----------------- | ------------------- | ------------------- |
| `pf-tabs`         | `pfTabChange`       | `{ value }`         |
| `pf-accordion`    | `pfExpandedChange`  | `{ value, values }` |
| `pf-tree-view`    | `pfSelectionChange` | `{ value }`         |
| `pf-button-group` | `pfSelectionChange` | `{ value, values }` |
| `pf-calendar`     | `pfSelectionChange` | `{ value }`         |
| `pf-carousel`     | `pfSlideChange`     | `{ index }`         |
| `pf-resizable`    | `pfResize`          | `{ size }`          |

## Styling

Two mechanisms, and the difference matters.

**Custom properties cross a shadow boundary.** Every `--pf-*` alias the React
components read is read by the elements too, so a theme set on `:root` — or on
any ancestor — reaches inside. This is also how a group tells a child element
what it needs: `pf-header-navigation` sets `--pf-nav-item-*` on itself, and the
`pf-nav-item`s slotted into it resolve those inside their own shadow roots.

```css
:root {
  --pf-button-primary-bg: rebeccapurple;
}
```

**Selectors do not.** A consumer's stylesheet cannot reach a shadow-internal
node, so every element exposes the boxes worth styling as `::part()`. Each
one is listed on the element's own page.

```css
pf-input::part(input) {
  font-variant-numeric: tabular-nums;
}
```

Dark mode is `[data-theme='dark']` on an ancestor, with no per-element
handling.

## Icons

The elements ask for icons by **role**, such as `close`, `next`, `search` or
`warning`, not by Font Awesome name. One `registerIconSet()` call from
`@pitchfork-ui/core` swaps every icon they draw for Font Awesome Pro, Lucide
or a set of your own. What you register wins over the built-in glyphs.
Register at startup, before the first render. Foundations → Icons lists the
roles and has an example for each set.

```ts
import { registerIconSet } from '@pitchfork-ui/core';
import { X, ChevronDown } from 'lucide';

registerIconSet({ close: X, 'chevron-down': ChevronDown });
```

## Where the element API differs from the React one

Most components take the same props. The differences are all consequences of
the platform, and each one is a decision rather than an omission.

**Data-driven components take child elements, not arrays.** The React
`Select` takes `options`; `<pf-select>` takes `<pf-option>` children and the
consumer loops in their own template. The same for `pf-tabs`, `pf-table`,
`pf-tree-view`, `pf-command-palette`, `pf-pie-chart` and the rest. It is more
markup and it is the right shape: a `ReactNode` in a prop has no equivalent
here, and a slotted child is something a framework can key, reorder and bind
to.

**A group's legend is made of its children.** A slot renders its assigned
content once and in one place, so a legend built inside a chart's shadow root
could never reach labels that live in the light DOM. `pf-pie-slice` and
`pf-radar-axis` therefore draw their own legend rows, and the chart pushes
down the two things only it knows: the colour and the share.

**Some names are attributes where React takes a node.** `pf-radar-axis` takes
`label` as a string because the chart draws each name inside its own SVG, and
an SVG `<text>` cannot hold arbitrary markup in either layer.

**A few props are renamed, because the platform owns the name.**
`pf-sparkline` takes `animated`, not `animate`: `Element.prototype.animate` is
the Web Animations API, and a prop that shadows a prototype member fails the
build. `pf-chart-series` takes `seriesKey` for the same reason `key` is
unavailable.

**Form controls are form-associated.** `pf-input`, `pf-checkbox`,
`pf-file-uploader` and the rest use `ElementInternals`, so their values reach
`FormData`, constraint validation works, and a reset restores the value the
control started with. A plain `<input>` inside a shadow root does none of
that — and neither does a React `contenteditable`, which is why
`<pf-rich-text-editor>` reaches a form where `RichTextEditor` does not.

**Overlays are `popover`s and `<dialog>`s, not portals.** `createPortal` has
no equivalent in a shadow root, and a positioned element there is clipped by
any ancestor's `overflow`. A `popover` opened from a shadow root is promoted
to the top layer and escapes both, and `<dialog>.showModal()` brings the focus
trap, Escape and the backdrop with it.

## Browser support

Safe to depend on, and depended on: custom elements, shadow DOM,
constructable stylesheets, `::part()`, `ElementInternals`, `<dialog>` and
`popover`.

Used only where there is a working fallback: cross-root ARIA element
reflection, which `pf-command-palette` feature-detects — without it the arrows
and Enter still work and the active option simply is not announced.

Deliberately unused: CSS anchor positioning, scoped custom element registries
and `:host-context()`. Those are the three that quietly make a library
Chromium-only.
